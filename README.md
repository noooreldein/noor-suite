## لماذا Noor Suite؟

معظم أنظمة إدارة الأعمال العربية إما سحابة إيجارية تقفل بياناتك، أو ملفات Excel مبعثرة. Noor Suite نظام واحد متصل:

- **قيد مزدوج حقيقي** — كل فاتورة بيع أو شراء أو مرتجع أو تسوية بتنشئ قيداً متوازناً في دفتر اليومية تلقائياً، بميزان مراجعة وقائمة دخل وميزانية عمومية لأي فترة.
- **شركة كاملة، مش مستخدم واحد** — مساحة عمل لكل منظمة، دعوات بكود، وأدوار (مالك / مدير / محاسب / كاشير / أمين مخزن / مبيعات) مفروضة على مستوى قاعدة البيانات.
- **فروع ومخازن حقيقية** — مخزون منفصل لكل فرع، تحويل بين الفروع بسجل حركة، وكل عملية بتحاسب على الفرع النشط.
- **POS جاد** — ورديات كاشير بتسوية درج، دفع متعدد (نقدي/بطاقة/آجل)، مسح باركود، ومرتجعات مربوطة بالفواتير.
- **خصوصية كاملة** — استضيف النظام عندك (self-hosted)، بياناتك في مشروع Supabase تملكه أنت، بلا اشتراكات وبلا رسوم.
- **خفيف وسريع** — بدون أي مكتبة تشغيل خارج React؛ الرسوم البيانية SVG مكتوبة يدوياً، ويعمل كتطبيق مثبت (PWA) أوفلاين بوضع الزائر.

## البنية التقنية

```
src/
├── modules/        # كل موديول مستقل (POS، محاسبة، مخازن …) — قابل للفصل
├── store/          # طبقة بيانات واحدة: React context + write-through للسحابة
├── lib/
│   ├── accounting.ts   # محرك القيد المزدوج: دليل الحسابات، ترحيل، ميزان، قوائم
│   ├── backend.ts      # Supabase: مزامنة، طابور إعادة محاولة، نسخ احتياطية
│   └── branches.ts     # مخزون لكل فرع + تحويلات
├── components/     # نظام تصميم موحد (Table, Modal, Badge, charts …)
└── i18n/           # عربي/إنجليزي RTL/LTR كامل
```

- **عمليات ذرّية على السيرفر**: البيع والاستلام والتحويل بيتطبقوا كمعاملة واحدة (PostgreSQL function بقفل صفوف المنتج) — أي انقطاع شبكة أو جهازين شغالين مع بعض مستحيل يسيبوا نصف عملية أو يضيعوا تحديث مخزون.
- **Write-through sync**: كل عملية بتتكتب محلياً فوراً (الواجهة مبتستنىش الشبكة) وتتزامن سحابياً، مع طابور إعادة محاولة دائم لو النت قطع.
- **عزل على مستوى القاعدة**: Row-Level Security على كل جدول — العرض لأعضاء المنظمة، الكتابة حسب الدور، وحذف القيود للمالك فقط.
- **كشف تعارض الأجهزة + نسخ تلقائية**: نسخة احتياطية سحابية كل 24 ساعة (آخر 7 نسخ) مع استعادة بضغطة، وسجل مزامنة لكل تعارض.

## التشغيل

```bash
git clone https://github.com/noooreldein/noor-suite.git
cd noor-suite
npm install
npm run dev        # تشغيل محلي — وضع الزائر يعمل فوراً بدون أي إعداد
```

### ربط السحابة (اختياري)

النظام يعمل محلياً بالكامل. لتفعيل الحسابات والمزامنة:

1. أنشئ مشروعاً على [Supabase](https://supabase.com) (الخطة المجانية تكفي).
2. من لوحة المشروع: **SQL Editor → New query** — الصق محتوى `docs/supabase-schema.sql` كاملاً ونفذه.
   السكربت **idempotent** (كل أوامره `IF NOT EXISTS` / `CREATE OR REPLACE`): ينشئ كل الجداول المنظمة (ns_orgs/ns_members/ns_invites)، جداول البيانات الـ16 بعمود org_id وسياسات RLS بمصفوفة أدوار لكل جدول، الدوال (ns_my_orgs، ns_orgs_with_roles، ns_join_org، ns_apply_op)، triggers لـ updated_at، والمنح — ويصلح للتشغيل على مشروع فارغ أو قائمة موجودة.
3. فعّل التسجيل: **Authentication → Providers → Email**، و(اختيارياً) عطّل تأكيد البريد من **Authentication → Emails** لتسجيل فوري.
4. ابنِ الواجهة بمفاتيح مشروعك:
   ```bash
   VITE_SUPABASE_URL=https://<ref>.supabase.co \
   VITE_SUPABASE_ANON_KEY=<anon-key> npm run build
   ```
   بدون متغيرات بيئة تعمل النسخة على النطاق المستضاف المدمج (المفاتيح في `src/lib/backend.ts` احتياطية). **لا تستخدم مفاتيح منصات أخرى مثل service_role في الواجهة أبداً** — كل الأمان قائم على RLS + المفتاح العام.
5. ارفع مجلد `dist` على أي استضافة ثابتة (GitHub Pages، Vercel، سيرفرك).

التفاصيل الكاملة في `docs/DEPLOYMENT.md`.

### اختبارات تكامل قاعدة البيانات (Integration)

بالإضافة لوحدات الواجهة، فيه سلسلة تكامل حقيقية تشتغل على قاعدة Supabase بحسابات مؤقتة قابلة للحذف:

```bash
SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<key> node tests/integration/suite.js
```

نتائج آخر تشغيل (v3.2.0، 2026-10-25، على قاعدة Supabase حقيقية — 9/9):

| السيناريو | النتيجة |
|---|---|
| 5 مبيعات متزامنة على نفس المنتج | PASS — نزل بالضبط 5 (صفر تحديثات مفقودة) |
| بيع كمية أكبر من المتاح | PASS — رفض نظيف، لا فاتورة ولا قيد ولا تغيير مخزون |
| تكرار نفس العملية (opId) بعد ضياع الرد | PASS — تنفذ مرة واحدة فقط |
| عزل شركتين (قراءة/كتابة/تشغيل RPC) | PASS — لا وصول من شركة لأخرى |
| هجوم المعرفات العابرة للشركات (كتابة فوق صف شركة أخرى بنفس id) | PASS — مرفوض والصف الأصلي سليم |
| هجمات مصفوفة الأدوار عبر RPC (كاشير على القيود والدفتر، جدول غير مسموح) | PASS — مرفوض بـ forbidden_role / forbidden_table |
| بيع → مرتجع → تحويل → استلام مشتريات | PASS — المخزون متطابق رياضياً وكل القيود متوازنة (مدين = دائن) |
| نسخة احتياطية: تخزين → تدمير → استعادة حقيقية | PASS — البيانات تعود كاملة ومخفية عن غير الأعضاء |
| دورة حياة الدعوة: انضمام / إعادة استخدام / منتهية | PASS — الانضمام ينجح والتكرار والمنتهية يرفضان |

**براهين التثبيت (نفس السكربت، ثلاث مسارات):**
- تشغيل متكرر على قاعدة موجودة (idempotent): PASS — بلا أخطاء وبلا فقدان بيانات
- ترقية قاعدة قديمة أحادية المستخدم (بدون org_id/updated_at): PASS — الأعمدة تُضاف والسياسات تُنشأ
- تثبيت من الصفر على قاعدة فارغة: PASS — 21 جدولاً و5 دوال و75 سياسة و20 تريغراً في تشغيلة واحدة

**النسخ الاحتياطية**: تُنشأ نسخة تلقائية كل 24 ساعة عند فتح النظام من أي جهاز (شرط وجود بيانات فعلية، وإحلال النسخ الفارغة)، ويُحتفظ بآخر 7 نسخ لكل شركة، مع استعادة يدوية كاملة من الإعدادات تعيد دفع البيانات للسحابة.
